# 多模型協作設計原則

給 Multi-Agent Studio 之後設計「多個 AI 成員分工」時參考。這些是原則，不是已實作的功能。

來源：2026-10-09 一篇 X 文章（@eng_khairallah1，“How to Build a Multi-Model Team of AI Agents”）。已對照 Anthropic 官方模型資料查證，只保留站得住的觀念；文章中錯誤或無法驗證的數字沒有收錄。

## 1. 規則交給程式，不交給 AI

計數、日期計算、金額或用量上限、權限判斷、刪除等不可逆動作，一律由程式決定。交給模型判斷，等於把一定正確的規則變成「大概正確」。

本專案已在做：runtime 清理只依 PID 樹、未知 owner 絕不 kill（見 [runtime-ownership.md](runtime-ownership.md)）。

## 2. 成員之間交接文件，不轉傳對話

一個成員做完後，交給下一個的是一份整理好的交接文件，不是整段對話：

- 被要求做什麼
- 查到什麼
- 決定了什麼、為什麼
- 還有什麼沒解決

原因：接手的模型看不到前一個的對話、工具結果與推理；而且新模型的 thinking 只綁定在產生它的那個模型上，其他模型會直接略過。交接文件同時也是出事時的稽核紀錄。

## 3. 重要產出由不同家的模型審查

同一個模型審自己的作品，會帶著相同的盲點。重要產出由另一家模型審（例如 Claude 寫、Codex 審，或反過來）。

審查要設回合上限，例如最多 3 輪，還談不攏就交給人決定，避免兩個模型無限爭論燒預算。

## 4. 分派不確定時往上，不往下

自動分派任務時，如果判斷不確定，就交給較強的模型或交給人，不要為了省錢交給較弱的。每次分派都記錄原因，之後才能找出被分錯的類型。

## 5. 每個成員都要有備援，並處理「拒絕」

- 某家服務出錯或逾時時，改由下一個成員接手，最好是另一家，不要整條流程停擺。
- 模型可能拒絕某些請求（Claude API 會回 `stop_reason: "refusal"`）。拒絕不是答案，要先檢查再讀內容。

## 6. 先量再分流

- 分派哪個模型做哪件事，要用自己的真實任務測過（20～50 筆、有已知正確答案），比較品質、每個完成任務的成本、等待時間；廠商公布的跑分只能拿來縮小候選名單。
- 在做「多模型分流」之前，先試「同一個強模型、調低 effort」，常常就夠用，也簡單得多。
- 用量小的時候，一個好模型就是正確答案；多模型分流的複雜度只有在量大或出錯代價高時才划算。

## 7. 多一家服務，就多一家拿到資料

每多接一家模型服務，就多一家公司收到你的資料。含個資或機密的任務，只送給已確認資料政策的服務，必要時固定只走一家。
